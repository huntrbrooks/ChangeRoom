# Subscriber generation jobs

For a new staging database, run `schema.sql` and `migration_add_credits_ledger.sql` as the Vercel application database owner. For this complete launch, confirm `clothing_item_offers`, `user_profiles` and `user_outfits` exist, then apply `migration_subscriber_billing_v2.sql`, `migration_tryon_jobs.sql`, `migration_account_closure_prerequisites.sql`, `migration_account_closure.sql` and `migration_tryon_ops.sql` in that order. Existing production prerequisites were inspected separately; follow the [cutover inventory](../docs/operations/production-cutover-inventory-2026-11-04.md) instead of replaying historical migrations blindly. These scripts require an explicit deployment step: there is no runtime schema creation for the job table. Vercel issues intents and reads private results as the table owner. If using a non-owner web role, intentionally configure a scoped policy and grants first; the migration enables RLS and grants no public table access.

Render requires **TRYON_DATABASE_URL** for the same database, using TLS and a dedicated non-owner, non-superuser login with CONNECT, USAGE on schema public, and only EXECUTE on the following job functions. Do not grant the Render login table access, ownership, membership in the web role, or BYPASSRLS. Verify inherited database privileges with the actual roles (including the grants inherited from PUBLIC). Keep the credentials server-side in Render, separate from the Vercel database owner. Example grants after creating a dedicated role named `tryon_worker`:

```sql
GRANT USAGE ON SCHEMA public TO tryon_worker;
GRANT EXECUTE ON FUNCTION public.tryon_claim(uuid,text),
  public.tryon_settle(uuid,text,bytea),public.tryon_extra(uuid,text,text) TO tryon_worker;
```

Set Render `BACKEND_AUTH_MODE=clerk` and the correct `CLERK_ISSUER`; configure `CLERK_AUDIENCE` if a custom backend token template sets an audience. Set Vercel `NEXT_PUBLIC_API_URL` and Render `ALLOWED_ORIGINS` to the staged hosts. Job generation always requires a signed Clerk user subject even if other backend endpoints allow a service key. The merchant pitch route cannot use a service key to generate on this consumer path. If granting staff unlimited jobs, explicitly list their verified Clerk IDs in Vercel `TRYON_PRIVILEGED_USER_IDS`; email or browser-provided flags never authorize work.

The subscriber chooses photos locally and posts them directly to Render only on Generate. The web service issues an owner-bound job UUID valid for five minutes. Render consumes it once after input validation, atomically reserving one trial or one credit. On success the worker re-encodes the image without metadata, watermarks actual trial bytes, and commits a private result and settlement atomically. The image is served only via the web user's Clerk session; a recent-looks link recovers a completed result after a network interruption. A repeated provider HTTP request is rejected. Failure restores exactly the reserved funding. Results are limited to 2.5 MB, 24 hours and owner-only access. A provider returning only a remote URL is rejected and refunded rather than fetched. Shopping and identification each consume one separate permission on a successful job within 15 minutes.

Run `SELECT public.tryon_sweep()` at least every five minutes as owner. It also runs on new intents. It refunds up to 100 running jobs older than 15 minutes per sweep (worker provider timeout: 8 minutes), clears at most 100 expired image payloads, and cleans at most 500 completed/abandoned rows older than 30 days per run. Reads independently stop after 24 hours even if the scheduler fails. Alert on expired running jobs, aged image bytes, sweep errors, duplicate/refund anomalies or growing backlog; reduce the interval/increase batch throughput if needed. Include this table in the account deletion process and disclose separately retained financial ledger entries/backup retention. Remove or protect historical public originals; disabling Render's static mount cannot revoke existing R2/public links.

Before paid launch: verify an anonymous visitor and a second user cannot open the same result; deliver an actual inline provider image and real HEIC input in the target staging build; stop waiting/refresh/reopen a completed job; confirm the two role grants, credit and trial accounting, private response headers, retention/purge and pricing match the customer offer. A lost acknowledgement of a committed result should be resolved by checking recent looks, never by issuing a blind second generation. Keep generation disabled until both stacks and schema are updated together; do not roll back to the browser-settled version.

Local verification (no live providers): use a disposable local database named `jobs_test`. Set `TRYON_TEST_DB_URL` to that database and run `python -m pytest backend/tests` using backend requirements. The integration tests apply base/job SQL to that database and exercise concurrency using real connections. Do not point tests at staging or production.
