# Subscription release and support runbook

New sales: Creator A$24.99 / 25 credits, Power A$49.99 / 70, both per month. One-time packs are 10/30/100 credits for A$14.99/A$34.99/A$89.99 respectively. New verified accounts receive one standard free look; existing trial balances are unchanged. There is no card-backed trial, annual billing, proration grants or new seasonal sales. Unused purchased credits carry over, including after cancellation. One settled subscription-create or subscription-cycle invoice adds the relevant allowance once per subscription period. A decline freezes generation until Stripe clears the invoice; use the authenticated billing portal to fix it.

1. Keep acquisition closed. Inventory existing customers, live subscriptions, legacy promises and open sessions before switching handlers. Honour existing contracts; customers on different allowances require an explicit migration or separately priced legacy plan. Do not silently switch them to 25/70. Resolve duplicates and unmapped prices; finish/expire open legacy checkouts. Record balances and reconcile historical periods; initial legacy grants were resets without invoice IDs. Control delivery/replay across cutover so an old and new handler cannot both settle a newly paid first invoice.
2. Apply the base schema/ledger, then `database/migration_subscriber_billing_v2.sql`. Tables are additive. Keep the migration timestamp unchanged on retries. A positive historical invoice predating this timestamp without a matching ledger entry goes to operator review instead of granting twice. Acknowledge it only after comparing the Stripe invoice, period, customer and historical ledger and recording the resolution. Do not rerun a credit grant blindly. Roll back the app behind a closed sales gate; keep financial tables and evidence intact.
3. Set matching frontend and server price IDs in the same Stripe mode, validate AUD amount/interval/active state, and reconcile registered subscription customers. Limit the pilot portal to payment-method updates, invoices and period-end cancellation; disable plan changes/prorations until separately tested. Configure receipts, recovery emails and smart retries. Confirm Stripe’s signing secret and snapshot endpoint version; subscribe to checkout completion/async success, payment-intent success, subscription created/updated/deleted/paused/resumed, invoice paid/payment_succeeded/payment_failed/payment_action_required/marked_uncollectible. Set an alert for non-2xx webhook delivery and `stripe_billing_event_requires_attention`.
4. In Stripe sandbox use ordinary accounts, each monthly offer and a pack. Check two concurrent checkout tabs; cancelling checkout charges nothing. Buy a pack before using a free image, then subscribe. Compare balances on first paid invoice with and without visiting the return URL. Replay the same event after spending; advance a test clock to renewal, decline the renewal, update the card in /billing, pay it, cancel at period-end, advance another period and confirm no charge. Replay old cancellation/failure after resubscribing. Retain redacted invoice, event, job and ledger identifiers with expected balances.
5. During pilot, run `scripts/agent/run-with-secrets.sh node frontend/scripts/audit-subscriptions.cjs YYYY-MM-DD` (install frontend dev dependencies for the pg CLI adapter). The date is UTC; exit 0 means all recognized paid recurring invoices in range matched a grant and owner, exit 2 flags exceptions, exit 1 means the audit failed. Check Stripe webhook failures as well: this deliberately small audit is not a complete merchant reconciliation. Track outstanding signed events and duplicate subscriptions. For a justified manual refund or dispute, record invoice/payment, corresponding ledger entries, credits already used, exact balance adjustment and support decision. Use tested recovery and keep receipts; neither a Stripe refund nor a DB adjustment alone proves both systems agree.
6. Run database lifecycle tests only against a disposable local database ending in `_test`: from frontend, `BILLING_TEST_DATABASE_URL=postgresql://… npm test -- --runInBand subscription-billing-postgres subscription-lifecycle`. They use synthetic users/transactions in a temporary schema and do not call Stripe. Stripe sandbox scenarios and production provider configuration still require operator verification.
