# One-time pack release and existing subscriber support

**Sales remain paused. The only approved future acquisition path is a one-time pack, after the operator verifies the complete paid customer journey and explicitly opens the pack gate.** No new subscriptions, card-backed trials, seasonal promo or Payment Links. The API never creates or resumes subscription Checkout Sessions, even when pack checkout is enabled. Existing subscribers keep portal access, cancellation, payment recovery, invoicing and period credit fulfillment.

| Eligible one-time pack | Single AUD payment | Credits |
| --- | ---: | ---: |
| Starter | A$14.99 | 10 |
| Value | A$34.99 | 30 |
| Pro | A$89.99 | 100 |

Read-only merchant check, 4 November 2026: the three server-mapped live prices and products were active. Each price was one-time, in AUD, at the amount shown; both its credit metadata and its product description matched the listed allowance. The historical A$14.99 / 20-credit seasonal product remains recognizable for old purchases only. The former browser mapping for the Pro pack referred to a recurring item; new clients send a stable SKU, the server selects its own price, and runtime checks reject mismatched type, amount, currency, product status or credit metadata. This provider check is **not** a purchase or delivery rehearsal.

1. **Stay closed until verified.** Inventory existing customers, subscriptions, legacy promises, balances and open hosted sessions. Keep direct payment links disabled; an app switch cannot revoke previously issued external checkout URLs. Honor all existing contract terms and already-purchased credits. Pre-cutover subscription grants may be anonymous balance resets: inspect the ledger and invoice before any historical correction. Do not silently change existing allowances.
2. **Prepare an isolated deployment.** Use a ChangeRoom-specific Stripe sandbox, isolated auth/DB/worker/storage, and sandbox prices with exact active product/amount/cadence and `price.metadata.credits`. Never run the tests against a preview with live credentials. Apply base schema/ledger and `database/migration_subscriber_billing_v2.sql`; retain the original migration timestamp across retries. Reconcile old signed events so old and new handlers cannot both grant a period. Keep public acquisition and provider Payment Links disabled throughout the rehearsal.
3. **Prove each proposed pack using an ordinary account.** Verify advertised credits and currency in the app and hosted Checkout, abandon Checkout (no charge), decline (no grant), complete payment without returning to the site (exactly one grant), then return and replay signed payment events (no duplicate). After spending one credit on a delivered result, repeat the replay and compare wallet with ledger. Exercise generation failure/refund and a customer support contact, invoice/receipt delivery, and operator reconciliation in both systems. Preserve only redacted evidence. A Stripe configuration mismatch blocks that pack; missing evidence blocks launch.
4. **Keep existing subscriber servicing working.** Verify the authenticated portal, invoices, email receipts, retry/recovery notices and cancellation. Limit the portal to payment-method updates, invoices and cancellation unless plan changes have been explicitly approved and tested. Use sandbox fixtures or clocks for replays, renewal, decline, recovery, cancellation and stale events on an *existing* subscription. No customer should be able to start another subscription through the app. Configure snapshot webhook events: checkout completion/async success, payment-intent success, subscription created/updated/deleted/paused/resumed, invoice paid/payment_succeeded/payment_failed/payment_action_required/marked_uncollectible. Alert on HTTP failures and `stripe_billing_event_requires_attention`.
5. **Operate and recover.** Run `scripts/agent/run-with-secrets.sh node frontend/scripts/audit-subscriptions.cjs YYYY-MM-DD` for existing subscriptions (install frontend dev dependencies for the pg adapter). It compares recognized paid initial/renewal invoices, owner and recorded grant in UTC. Exit 0 = compared rows match; 2 = exceptions; 1 = incomplete audit. For packs compare paid payment intents to each customer's grant by payment intent ID; never blindly regrant or rerun historical repair scripts. For an approved refund/dispute record receipt, ledger entries, credits already spent and remedy. Account deletion/cancellation must preserve required financial records and stop future charges as promised.
6. **Local regression tests.** From `frontend`, use `npm test -- --runInBand pack-checkout subscription-lifecycle`. The database suite additionally requires an isolated local database ending in `_test`: `BILLING_TEST_DATABASE_URL=postgresql://… npm test -- --runInBand subscription-billing-postgres`. These tests do not contact Stripe. Live configuration, sandbox end-to-end results and explicit pack release signoff are separate gates.
