# Missing cleanup-run monitoring

The subscriber operations workflow sends a success heartbeat only after `scripts/ops/sweep.py` completes cleanup and all aggregate checks successfully. A failed or missing run sends no success. GitHub failure email remains useful, but cannot detect an execution that never starts. GitHub documents that scheduled workflows can be delayed/dropped and public-repository schedules can be disabled after 60 days without repository activity: [schedule limitations](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## Setup before unattended sales

1. Use an owner-controlled Healthchecks.io account and create separate production and staging checks. Its [free plan](https://healthchecks.io/pricing/) supports 20 checks; no paid plan is required for these two. Set a simple **5-minute period and 15-minute grace** to alert when the last successful ping is over 20 minutes old. Enable and verify email delivery to the named operator. Do not treat a dashboard configuration as receipt evidence.
2. Store each private UUID ping URL in the matching protected GitHub Environment as `CHANGEROOM_SWEEP_HEARTBEAT_URL`. The client accepts only `https://hc-ping.com/<lowercase canonical UUID>` with no query, fragment, credentials, extra path or port. Do not put it in code, chat, logs or a public badge. It can falsely signal health if disclosed. No management API key is needed in GitHub.
3. Keep the existing main-only environment policy and workflow default-branch guard. The heartbeat runs in the same sweep job and inherits its environment, concurrency control and three-minute timeout. The client makes at most two attempts, with a 10-second socket I/O timeout and a one-second retry delay. This is not a wall-clock limit per attempt; the workflow timeout bounds the overall job. It refuses redirects and requires HTTP 200 with the exact body `OK`; a 200 response saying the check does not exist is a failure. Only an empty POST is sent: no customer data, DB credentials, logs or aggregate counts. See the provider's [ping API](https://healthchecks.io/docs/http_api/) and [privacy notice](https://healthchecks.io/privacy/).
4. A missing heartbeat secret fails **every production run**, including a manual prelaunch run, and any scheduled check. The one setup exception is a manual staging run without a configured URL: cleanup still runs, and the heartbeat step explicitly says monitoring is unverified. Once a staging URL is configured, invalid URLs or failed delivery fail the job. Do not cite an unconfigured staging success as proof that this gate passed.
5. Enable production scheduling only after the production origin, restricted DB role, monitor and alert recipient are verified. A heartbeat error fails the workflow after cleanup has already completed; it does not roll back cleanup or charge a customer. Diagnose the monitor before rerunning, and never move the heartbeat before the sweep or add `always()`/`continue-on-error` to disguise failures.

## Acceptance evidence

- Run the trusted default-branch staging workflow with a configured staging URL; both the sweep and heartbeat must pass, and the check's last-ping time must match.
- Prove a **missing** heartbeat alert and receipt using the staging check only. Let a check become late by withholding staging pings after a successful test; do not suspend production cleanup or change production credentials. If regular staging cleanup is operating, use a separate temporary test check for the missed-ping drill. Record last success, expected threshold, alert receipt and subsequent recovery. An explicit failure signal alone does not test absence detection.
- After production is enabled, observe at least two successful scheduled sweep executions and matching production pings. Keep the existing failure-email evidence. Record the exact workflow source and run URLs privately without ping URLs.
- On an alert, inspect the latest workflow and scheduler enablement, then perform an authorized manual sweep and investigate any residual aggregate backlog. Recovery requires a new successful ping and healthy counts. Do not delete financial evidence or customer files manually to silence the alert.

The free service retains only 100 ping log entries (approximately eight hours at a five-minute cadence); retain GitHub run receipts as operational evidence. A named operator must monitor the mailbox. This is a lightweight launch control, not a guaranteed alert-delivery SLA.

## What the heartbeat does not prove

Result and recent-look routes independently reject previews older than 24 hours, even when the scheduler fails. The sweep separately clears up to 100 expired live result payloads per run, refunds interrupted jobs, and removes bounded old job metadata. New try-on intents also invoke the sweep, but customer activity is not a substitute for scheduled cleanup. A delayed sweep can delay live payload removal and unattended refunds. A healthy ping confirms the sweep and its aggregate thresholds passed; it does not prove physical erasure from PostgreSQL storage, backups, legacy storage or AI providers. Keep the privacy notice's distinction between access expiry, routine live cleanup and backup/provider retention.
