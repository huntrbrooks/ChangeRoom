## Which application is being released?

The subscriber candidate adds authenticated Next.js `/api/try-on/jobs` and `/api/try-on/recent` routes, Postgres job functions and the separately deployed Render FastAPI worker. See [subscriber job funding, role grants and expiry](../../database/TRYON_JOBS.md). Check the release manifest before a rollout. The documented legacy Next `/api/try-on` and `/api/upload-urls` do not exist in the November baseline. Older builds used browser-managed credit holds and browser-driven finalization. Do not unblock purchases on those builds. Keep customer billing management and verified webhooks available during an incident.

## Before the first paid account

1. Record the **same release** (frontend SHA, worker SHA, migration state and deployment URLs) in the private handover. Confirm staging and production have separate Clerk, Stripe endpoints/keys, databases, storage, and provider budgets. Check domains, CORS, HTTPS, issuer and audience, restricted database grants, and the actual hosted Render **service** plan. The blueprint is not proof of live settings. In Render Events determine the reason for any suspension. Never change plans or resume an unpatched worker to clear a health alarm.
2. Use the database owner's migration plan. Snapshot **before** changes. The new job tables depend on `schema.sql`/credit ledger. Apply `migration_subscriber_billing_v2.sql`, `migration_tryon_jobs.sql`, account-closure prerequisites and `migration_account_closure.sql`, then `migration_tryon_ops.sql`. Validate migrations on a restored staging clone; do not blindly re-run every historical `migration_*.sql` alphabetically. Restrict Render to EXECUTE of its allowed worker functions; keep table-owner credentials away from the worker and monitor. Test with the real non-owner roles.
3. Enable and prove the controls described below in staging, then on the candidate production revision. Inspect backup restore points and storage lifecycle settings; run a representative restore in isolation. Verify no images, signed URLs, credentials, receipt payloads or emails appear in application logs, alert output or the public status page. Check AI/analytics settings and retention agreements including fallback processors, account deletion and backup expiry. Verify merchant identity, sale countries/minimum age, currency/tax display, affiliate disclosure, refund handling, consumer rights and privacy notices with the business owner. Australian references: [ACCC consumer guarantees](https://www.accc.gov.au/consumers/buying-products-and-services/consumer-rights-and-guarantees) and [OAIC privacy policy guidance](https://www.oaic.gov.au/privacy/your-privacy-rights/your-personal-information/what-is-a-privacy-policy).
4. In a **test-mode** isolated release run the full signed-out → signup → trial → pack → paid plan → first result → save/reopen → support → renewal → decline/recover → cancel → deletion sequence. Test two people, mobile HEIF from a real device and desktop JPG; owner isolation, refund of interrupted work, concurrent last credit, duplicate/out-of-order webhooks, and a browser closing after purchase or generation. Simulate payment phases with Stripe test clocks, not a real customer. Confirm quantities/renewal terms in UI, Checkout, invoices, portal and ledger. Failed provider calls must not exhaust acquired credit. Restore the interrupted result by request ID without a second charge. Generated preview is approximate, not sizing advice.
5. Confirm the public `/status`, `/support` and `/billing` navigation while signed out and signed in. Keep proof with timestamps, no tokens or customer photos.
6. Release only when all gates pass. The application purchase flag, any Vercel firewall block, and Stripe Payment Links are independent. Prefer keeping standalone links disabled if the owned checkout is the only supported entitlement path. Do not reenable historical discount links by default. Verify signup and app billing management without placing an unapproved live charge. Watch the first sales window with a named operator.

## Monitoring and job cleanup

`.github/workflows/subscriber-operations.yml` runs public website/API liveness and a separate Postgres cleanup job. Configure GitHub Environments `staging` and `production` with HTTPS origins `CHANGEROOM_APP_ORIGIN` and `CHANGEROOM_API_ORIGIN` and encrypted `CHANGEROOM_SWEEP_DSN`. Use an unpooled PostgreSQL connection with verified TLS; the runner uses system roots. Issue a **dedicated login**, not the owner, with database CONNECT, schema USAGE and only:

```sql
GRANT EXECUTE ON FUNCTION public.tryon_sweep(), public.tryon_ops_counts() TO changeroom_sweeper;
```

Create the login and configure its password in the provider dashboard/secret manager; never put passwords in SQL history or commits. Confirm it can run both functions and **cannot** select customer rows or execute claim/settle/extra. `tryon_ops_counts()` exposes only totals. Confirm these two functions are still revoked from PUBLIC. Check owner role and search path after migrations.

Run the workflow manually for `staging`; it must go red on a bad health origin and on a broken grant, and green after correction. Use a staging fixture to prove old jobs refund once and old previews disappear. Then do one `production` run with unmodified production data only when the migration + retention schedule are authorized. Set repository variable `SUBSCRIBER_OPS_ENABLED=true` to opt into the 15-minute production schedule on the default branch. Require non-interactive environment access for the scheduled job. Do not **only** rely on a green workflow: enable failure notifications for the named operator, configure a separate dead-man check on the last successful sweep (alert if older than 45 minutes), stage one alert and confirm receipt. A delayed scheduler can delay physical deletion: recent result reads should independently reject expired results.

* Website probe expects the public status page and the FastAPI stack marker plus expected JSON within 15 seconds. This detects suspension/login redirects, not provider balance, payment success or generation quality. For outages inspect `X-Request-Id` in the two hosts and run a budgeted staging canary. Never use real photos for uptime checks.
* The sweeper releases interrupted running jobs older than 15 minutes, clears result payloads older than 24 hours and removes old job metadata after 30 days in bounded batches. The monitor flags remaining stale jobs (>20 min), image payloads (>25h), history (>31d) or ≥5 failed jobs constituting at least half of recent completions (30 min). Inspect aggregate counts; rerun once for a backlog. Investigate locks, limits, failed deployments or providers rather than increasing concurrency blindly.
* Configure Stripe failed-webhook/undelivered alerts and invoice failure notifications to the accountable operator/customer as appropriate. Configure provider budget and quota alerts; test delivery in staging. Weekly analytics email is not an outage alert. Review the account-closure queue daily: raise unresolved billing or >24h pending external media cleanup to support, verify external object removal before marking it complete, and do not erase the financial evidence required for a dispute.

## Incident, rollback and support

1. Triage impact with date/time, request ID, environment, feature, release SHA and Stripe invoice/event references. Do not copy photos, full URLs or payment data to tickets. Tell customers what is known on `/status`; do not imply the status notice verifies individual accounts.
2. If generation or entitlements cannot be trusted: refuse **new Checkout creation** at the edge and app, audit/disable only Stripe Payment Links that exclusively sell this product, re-list open app sessions. Existing subscriptions/credits, portal cancellation and signed webhooks must remain accessible. Do not bulk-cancel, refund, change plans or email users without owner approval. Keep a private inventory of previously active link IDs only, separately from credentials.
3. Compare provider incident history/limits and both release SHAs. Repoint frontend and Render to compatible known-good revisions **only behind the payment gate**. Do not roll back to unenforced generation, legacy public photo serving or unsigned checkout/credits. Normally keep additive database changes. If compatibility is uncertain, keep generation off, serve status/billing and fix forward. Do not down-migrate/destroy financial rows during incident response.
4. For a report of missing credits, cross-check ownership, Stripe paid/refunded status, billing ledger request/receipt and the job result. Retry the signed Stripe event only after fixing the cause; verify exactly one credit grant. Update card or cancel through `/billing`; confirm the portal’s effective date and no next charge. Do not promise a refund before owner review. For media deletion verify account ownership, inspect/reconcile the closure queue, object references and external providers; report exceptions accurately.
5. Rehearse the failing case, plus a cold start, failure recovery, sign-in, existing-account billing and cancellation in staging. Record operator sign-off before any reopening. Share only aggregate data with public status; keep redacted incident timeline, receipts and deploy IDs privately.

**Sandbox checkout:** Use a separate, access-controlled staging project (or a locally isolated environment) with a dedicated DB branch/bucket, Clerk test application, Stripe sandbox, test prices, webhook and staging Render service. The existing production-project checkout firewall rule must stay enabled. Only set `CHANGEROOM_ISOLATED_PREVIEW=true`, `CHANGEROOM_STAGING_API_HOST` and `CHANGEROOM_TEST_CHECKOUT=true` on the isolated preview. The server verifies test key modes and staging API hostname. Confirm database ownership independently; different variable names alone do not demonstrate isolation. The production checkout switch is false regardless of these settings.

**Account closure:** Signed Clerk deletion creates a durable tombstone, purges app images, refunds in-flight jobs and inventories legacy object references. It expires proven app-owned open checkout sessions and cancels proven app-owned subscriptions without new proration or an immediate invoice. Retry after transient Stripe failure. Check `account_closures.billing_state IN ('pending','review')` and outstanding `external_cleanup_at IS NULL` daily while the queue is nonempty. Resolve mixed subscriptions, missing metadata or historical prices manually against invoices. Treat legacy object keys/outfit paths as untrusted: verify the canonical bucket and ownership independently before removing an object. Reconcile affected processor/analytics/backup records using their actual retention settings; mark completion only after checking. Retain only necessary financial records and the minimal suppression record.
