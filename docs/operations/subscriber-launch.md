## Which application is being released?

The subscriber candidate issues an owner-bound job via Next.js `POST /api/try-on/hold`. The browser sends the job and photos to the separate Render FastAPI worker; after settlement, the signed-in customer can retrieve `GET /api/try-on/jobs/[id]/result` or list unexpired looks at `GET /api/try-on/recent`. PostgreSQL records funding, status and the private result. See [subscriber job funding, role grants and expiry](../../database/TRYON_JOBS.md). Check the release manifest before a rollout. The documented legacy Next `/api/try-on` and `/api/upload-urls` do not exist in the November baseline. Older builds used browser-managed credit holds and browser-driven finalization. Do not unblock purchases on those builds. Keep customer billing management and verified webhooks available during an incident.

## Monitoring and job cleanup

`.github/workflows/subscriber-operations.yml` runs public website/API liveness and a separate Postgres cleanup job. Configure GitHub Environments `staging` and `production` with HTTPS origins `CHANGEROOM_APP_ORIGIN` and `CHANGEROOM_API_ORIGIN` and encrypted `CHANGEROOM_SWEEP_DSN`. Use an unpooled PostgreSQL connection with verified TLS; the runner uses system roots. Issue a **dedicated login**, not the owner, with database CONNECT, schema USAGE and only:

```sql
GRANT EXECUTE ON FUNCTION public.tryon_sweep(), public.tryon_ops_counts(), public.closure_ops_counts() TO changeroom_sweeper;
```

Create the login and configure its password in the provider dashboard/secret manager; never put passwords in SQL history or commits. Confirm it can run all three functions and **cannot** select customer rows or execute claim/settle/extra. `tryon_ops_counts()` exposes only totals. Confirm all three functions are still revoked from PUBLIC. Check owner role and search path after migrations.

Run the workflow manually for `staging`; it must go red on a bad health origin and on a broken grant, and green after correction. Use a staging fixture to prove old jobs refund once and old previews disappear. Then do one `production` run with unmodified production data only when the migration + retention schedule are authorized. Set repository variable `SUBSCRIBER_OPS_ENABLED=true` to opt into the five-minute production schedule on the default branch. Require non-interactive environment access for the scheduled job. Do not **only** rely on a green workflow: enable failure notifications for the named operator, configure a separate dead-man check on the last successful sweep (alert if older than 20 minutes), stage one alert and confirm receipt. A delayed scheduler can delay physical deletion: recent result reads should independently reject expired results.

* Website probe expects the public status page and the FastAPI stack marker plus expected JSON within 15 seconds. This detects suspension/login redirects, not provider balance, payment success or generation quality. For outages inspect `X-Request-Id` in the two hosts and run a budgeted staging canary. Never use real photos for uptime checks.
* The sweeper releases interrupted running jobs older than 15 minutes, clears result payloads older than 24 hours and removes old job metadata after 30 days in bounded batches. The monitor flags remaining stale jobs (>20 min), image payloads (>25h), history (>31d) or ≥5 failed jobs constituting at least half of recent completions (30 min). Inspect aggregate counts; rerun once for a backlog. Investigate locks, limits, failed deployments or providers rather than increasing concurrency blindly.
* Configure Stripe failed-webhook/undelivered alerts and invoice failure notifications to the accountable operator/customer as appropriate. Configure provider budget and quota alerts; test delivery in staging. Weekly analytics email is not an outage alert. The sweep job also fails for any closure billing state `review`, `pending` beyond 30 minutes, or manual external cleanup outstanding more than 24 hours. No personal identifiers are emitted. Route this job’s failure to the named support operator; red workflow logs are not evidence a human saw them. Inspect the private queue: raise unresolved billing or >24h pending external media cleanup to support, verify external object removal before marking it complete, and do not erase the financial evidence required for a dispute.

Restrict that environment to the protected default branch in GitHub settings (a YAML guard cannot defend against a modified workflow on an arbitrary branch). The legacy `changeroom` project was observed to expose the same live Stripe secret and production Render base URL to its default Preview target as to Production; database values marked sensitive were not inspectable, so isolation has not been established. Do not deploy a candidate branch automatically or manually on that project’s Preview target. Manually build/deploy trusted revisions in a **separate**, access-controlled staging project using only its own credentials. Before any build compare scope metadata privately: no Production variables shared into the staging project (including DB aliases, provider keys, storage buckets, Clerk, Stripe, webhook and analytics). Set `CHANGEROOM_STAGING_DB_HOSTS` to comma-separated **exact** staging connection names (including pooled and direct hostnames), and `CHANGEROOM_STAGING_DB_NAME` to the dedicated staging DB name. Ensure every defined `POSTGRES_URL`, `POSTGRES_PRISMA_URL`, `DATABASE_URL`, and `POSTGRES_URL_NON_POOLING` points only at those targets. Confirm with the database provider that these are truly staging endpoints, not alternative aliases for the live DB. Use a restricted staging role and separate test Stripe prices; validate a signed-in test purchase/receipt and matching test-mode webhook before declaring it isolated. Never print URLs, webhook secrets or keys for this check.
