# Restore and reconciliation

**Scope:** Neon/PostgreSQL contains billing balances, an append-only credit ledger, user/media pointers and private short-lived job results. Files referenced by older wardrobe rows may live in object storage. Stripe is the authoritative external receipt/invoice history. A database backup alone cannot recreate a removed image, and a Stripe receipt alone cannot reconstruct a consumed credit.

**Before launch:** confirm provider backup/PITR retention, region and restore permissions in the actual project. For saved media, document whether versioning, a recoverable separate copy or an explicitly temporary-only promise is in place. A storage URL is not a backup. Separate operator access from runtime access. Record most recent recovery point and tested recovery time, backup encryption and expiry, including how deleted users/expired photos are suppressed after restore. Suggested small-launch targets for owner approval: maximum 24 hours of recoverable-data loss, 4 hours to reinstate billing/support; paid invoice/credit mismatches must be reconciled before new purchases. Record the accepted targets and evidence; these are not claims about the current host plan.

## Synthetic rehearsal (non-production only)

`python scripts/ops/recovery_drill.py --port <local-postgres-port>` accepts **only** a loopback connection, fixed user `crtest` and fixed database `recovery_test`. Create that disposable database first. Install `psql`, `pg_dump` and `pg_restore` of a compatible version and put them on PATH. The four tested tables must be empty. `PGPASSWORD` may hold a local test password. Neither live secrets nor Stripe/R2 connections are used.

The drill applies the candidate schema/migrations and creates one artificial account, two credits, a successful paid job, an abandoned paid job, two sweeps, and one local simulated external-media object and reference. It dumps the actual tables to a custom-format archive, copies the synthetic object separately, removes **only** the fixture rows and local object, then restores the data in FK-safe order with a single transaction. It compares the balance, ordered ledger/job state and result bytes, checks the reference resolves to matching object bytes, and verifies old result-image expiry. Temporary archives are private and removed when the script exits. `pg_restore` into a schema with existing constraints requires parent table data before dependent rows; the script explicitly orders the table list. If a local rehearsal fails, inspect or recreate the disposable DB only, never retry against a real deployment.

**4 Nov 2026 local rehearsal:** PostgreSQL 18.6; restored the account with one available credit, one confirmed debit and one release, five ledger entries, two jobs and one object pointer; result bytes and object contents matched. Repeated cleanup released the interrupted job once, and expired result bytes were removed. Fixture restore and comparisons took ~0.05 s; this tiny sample is **not a production RTO, Neon backup restore, real R2 fetch, or live Stripe reconciliation**.

**4 Nov 2026 provider settings:** Production project `polished-glade-65760282` reports a 86,400-second (24-hour) history-retention window. Current branch `br-snowy-brook-a7slxiau` is ready/default. Its automatic snapshot schedule is empty. The pre-migration snapshot `snap-autumn-math-a7hxpx0y` was created at 05:25:17 UTC and expires on 11 November; an earlier snapshot of the previous branch expires the same day. These are current recovery options, not a verified RPO/RTO or a durable scheduled-backup arrangement. The candidate stores temporary generated result bytes in PostgreSQL; a new object-storage recovery system is not required for that path. Legacy external-media recovery remains a separate inventory problem.

**Restore safety:** A snapshot rehearsal must explicitly use `finalize: false` and a separate target. The provider's default restore finalization can reassign the live compute. Do not finalize, move endpoints, change the default branch or overwrite production during a drill. Independently record the live endpoint-to-branch mapping before and after; an isolated restore is not proved merely by choosing a new branch name.

## Current account and deletion reconciliation

A separate deletion-storage platform is not required for this launch. Current Clerk account existence is independent of a restored application database; the access-controlled support inbox can retain verified full-account and photo-only deletion decisions. These sources must be available to the recovery operator for the oldest backup eligible for use, including manual snapshots older than the 24-hour PITR window.

1. Keep the restored application private with product access disabled. A closed purchase gate alone does not prevent an authenticated result route from serving restored photos. Enumerate immutable Clerk IDs across all restored profile, job and legacy personal-data tables; preserve existing closure records.
2. Verify the exact production Clerk instance with a known surviving control account, then check each restored account. A confirmed user-not-found response requires suppression. Authentication failures, rate limits, timeouts and ambiguous historical IDs require withholding access until resolved; never treat them as proof of either existence or deletion.
3. Reconcile current Clerk/Svix deletion events and verified support cases since the recovery point, including outstanding requests. Clerk existence covers fully deleted accounts; support records must also cover photo-only removal and app closure where the Clerk identity remains. Record only the user/asset identifier, scope, decision time and case/event reference needed for suppression, not the photos themselves.
4. Apply confirmed full closures using the database's `request_account_closure` function on the isolated copy. Do not call the application's `closeDeletedAccount()` wrapper in a drill: it can expire real Checkout sessions and cancel subscriptions. Apply photo-only decisions at their actual scope and run retention cleanup. Preserve financial evidence and unresolved external-media cleanup records.
5. Reconcile decisions and pending webhook deliveries arriving during the scan before exposure. A one-time existence scan is not atomic with cutover. Use trusted provider records or provider replay; do not reuse an archived signature as a new valid delivery.
6. Prove that deleted identities cannot recover product rows/bytes, late profile sync remains scrubbed and new reservations are denied, while the surviving control remains intact. Repeat suppression and compare results. Financial reconciliation remains a separate gate.

The earlier hosted drill used a synthetic later-deletion instruction. Before claiming this reconciliation gate passed, connect the real verified Clerk deletion/404 evidence to restored fixture data, prove operator access to the relevant event/support history, and exercise the final-delta procedure. This runbook does not claim those additional checks already passed.

## Provider drill required before accepting payments

1. Use a real provider-created recovery point on an **isolated** branch/database. Restore into it; never overwrite the live database in a rehearsal. Disable outgoing Clerk/Stripe webhooks, mail and all checkout/checkout retries on the restore environment. Use a private staging bucket/prefix and synthetic fixture customer. Record timestamp and elapsed time in a private release receipt; don't record the DSN.
2. For current database-held results, verify restored image bytes/hash and private access as the correct user; deny another user. Only if legacy external media is in the recovery scope, separately restore a synthetic saved object from its recovery copy and verify its hash/access. Check restored DB photo pointers, jobs, invoices, balances and ledger conservation. Do not restore publicly accessible photo links. Apply current Clerk account/deletion-case reconciliation and retention cleanup before any exposure; do not resurrect erased photos. Keep the original backup under its retention restrictions.
3. Compare Stripe paid invoices/packs after the backup time with the restored ledger by invoice/receipt ID. Handle refunds, disputes, cancelled customers and in-flight jobs separately; rerun reconciliation idempotently twice on isolated data and compare totals. Never issue a new real purchase or overwrite paid balances to force an apparent match. During a real recovery keep sales off until mismatches are accounted for and reviewed.
4. Verify independent privileged access recovery; record actually achieved RPO and RTO, ownership, next drill date, and any remaining object/ledger discrepancies. Delete the isolated restore under the retention policy when evidence is saved. Repeat on material storage/billing changes and periodically during paid operation.
