# Restore and reconciliation

**Scope:** Neon/PostgreSQL contains billing balances, an append-only credit ledger, user/media pointers and private short-lived job results. Files referenced by older wardrobe rows may live in object storage. Stripe is the authoritative external receipt/invoice history. A database backup alone cannot recreate a removed image, and a Stripe receipt alone cannot reconstruct a consumed credit.

**Before launch:** confirm provider backup/PITR retention, region and restore permissions in the actual project. For saved media, document whether versioning, a recoverable separate copy or an explicitly temporary-only promise is in place. A storage URL is not a backup. Separate operator access from runtime access. Record most recent recovery point and tested recovery time, backup encryption and expiry, including how deleted users/expired photos are suppressed after restore. Suggested small-launch targets for owner approval: maximum 24 hours of recoverable-data loss, 4 hours to reinstate billing/support; paid invoice/credit mismatches must be reconciled before new purchases. Record the accepted targets and evidence; these are not claims about the current host plan.

## Synthetic rehearsal (non-production only)

`python scripts/ops/recovery_drill.py --port <local-postgres-port>` accepts **only** a loopback connection, fixed user `crtest` and fixed database `recovery_test`. Create that disposable database first. Install `psql`, `pg_dump` and `pg_restore` of a compatible version and put them on PATH. The four tested tables must be empty. `PGPASSWORD` may hold a local test password. Neither live secrets nor Stripe/R2 connections are used.

The drill applies the candidate schema/migrations and creates one artificial account, two credits, a successful paid job, an abandoned paid job, two sweeps, and one local simulated external-media object and reference. It dumps the actual tables to a custom-format archive, copies the synthetic object separately, removes **only** the fixture rows and local object, then restores the data in FK-safe order with a single transaction. It compares the balance, ordered ledger/job state and result bytes, checks the reference resolves to matching object bytes, and verifies old result-image expiry. Temporary archives are private and removed when the script exits. `pg_restore` into a schema with existing constraints requires parent table data before dependent rows; the script explicitly orders the table list. If a local rehearsal fails, inspect or recreate the disposable DB only, never retry against a real deployment.

**4 Nov 2026 local rehearsal:** PostgreSQL 18.6; restored the account with one available credit, one confirmed debit and one release, five ledger entries, two jobs and one object pointer; result bytes and object contents matched. Repeated cleanup released the interrupted job once, and expired result bytes were removed. Fixture restore and comparisons took ~0.05 s; this tiny sample is **not a production RTO, Neon backup restore, real R2 fetch, or live Stripe reconciliation**.

## Provider drill required before accepting payments

1. Use a real provider-created recovery point on an **isolated** branch/database. Restore into it; never overwrite the live database in a rehearsal. Disable outgoing Clerk/Stripe webhooks, mail and all checkout/checkout retries on the restore environment. Use a private staging bucket/prefix and synthetic fixture customer. Record timestamp and elapsed time in a private release receipt; don't record the DSN.
2. Restore a known synthetic non-expired saved image independently from the bucket’s recovery copy. Verify object size/hash and signed access as the correct user; deny another user. Check restored DB photo pointers, jobs, invoices, balances and ledger conservation. Do not restore publicly accessible photo links. Apply the current tombstone/deletion register and retention sweep before any exposure; do not resurrect erased photos. Keep the original backup under its retention restrictions.
3. Compare Stripe paid invoices/packs after the backup time with the restored ledger by invoice/receipt ID. Handle refunds, disputes, cancelled customers and in-flight jobs separately; rerun reconciliation idempotently twice on isolated data and compare totals. Never issue a new real purchase or overwrite paid balances to force an apparent match. During a real recovery keep sales off until mismatches are accounted for and reviewed.
4. Verify independent privileged access recovery; record actually achieved RPO and RTO, ownership, next drill date, and any remaining object/ledger discrepancies. Delete the isolated restore under the retention policy when evidence is saved. Repeat on material storage/billing changes and periodically during paid operation.
