# Deploying the try-on API into a new provider account

The frontend, customer accounts, Stripe, ledger and support address do not need to change. Only the synchronous Python worker moves. The separate YOLO service is not part of the subscriber flow. Start from the reviewed release candidate and a new isolated staging project. Do not deploy a historical worker or copy an entire environment file from production. Keep production checkout and Payment Links closed.

| Option | Fit for this worker |
| --- | --- |
| **Google Cloud Run** | Recommended first rehearsal: one request can last beyond the worker's eight-minute model deadline. Use a 600-second request timeout, concurrency 1, min instances 0, max instances 1 initially, 1 CPU / 2 GiB as a starting point; measure memory and a real job before production. With this HTTP/1 Uvicorn container, requests are limited to 32 MiB; set `MAX_TOTAL_SIZE=31457280` (30 MiB) to leave room for multipart headers and leave the frontend at its matching default, `NEXT_PUBLIC_TRYON_MAX_UPLOAD_MIB=30`. [Provider limits](https://docs.cloud.google.com/run/quotas), [request-based billing](https://docs.cloud.google.com/run/docs/configuring/billing-settings). Model charges are separate from hosting. |
| **Railway** | Can host the container, but its edge can end a request after five minutes without data. This worker sends the image only when the job finishes. Prove the slow case or use polling before relying on Railway for eight-minute jobs. [Networking limits](https://docs.railway.com/networking/public-networking/specs-and-limits). |
| **Existing Render** | Least configuration change once the workspace billing suspension is resolved. Before any reactivation, secure the old service and check the effect on other services in that workspace. Recheck actual service settings, not just render.yaml. |
| **Vercel Functions** | Keep the website on Vercel. Moving this upload handler there unchanged would reject multi-photo requests over 4.5 MB; direct object uploads would need a separate design. [Function limits](https://vercel.com/docs/functions/limitations). |

1. In a project owned by the business, enable billing and set alerts for infrastructure and model usage separately. Select a region near the isolated database and consistent with your data commitments. Create a narrowly scoped worker identity with access to its own secrets only. No Stripe keys belong on the worker.
2. Build just [the worker container](../../backend/CONTAINER.md) for Linux. Deploy its digest to staging; initially restrict access while verifying its environment. Install isolated Clerk issuer, HTTPS frontend allowlist, restricted Postgres connection and model credentials via the provider secret store. Decide memory/concurrency limits from the measured load. No production provider keys, customer records or production DNS are needed for rehearsal.
3. For a browser test allow incoming HTTPS to the worker while retaining application-level Clerk verification on every image route. Point **only the isolated staging frontend** at it and rebuild (the URL is compiled into client code). Validate CORS from the intended origin, denial for anonymous requests, the body cap, five garments and a real mobile HEIF. Use a consented test photo to exercise the primary model and a controlled availability-failure fixture to exercise fallback. Verify failures are refunded and other accounts cannot fetch the result.
4. After the operator signs off on accounts, receipts, credits, results and restoration, prepare a separate production worker configuration. Change the production frontend API URL by rebuilding/deploying, with checkout still closed. Verify both stacks use the corresponding database and issuer. Smoke-test then open **only** the verified one-time packs; keep the old worker offline. Do not reconstruct the Stripe catalog, Clerk customers or balances just because the host changed.
